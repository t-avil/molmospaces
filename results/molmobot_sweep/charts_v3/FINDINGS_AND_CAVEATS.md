# Mobile-pick distribution-shift study — findings & caveats (v3, technical)

Clean re-run after fixing the v2 double-perturbation confound. Data on the 347-scene
scripted-IK-solvable set; matched seeds (paired per scene); 95% Wilson CIs.
Generated by `scripts/make_poster_charts_v3.py` (+ `scripts/poster_stats.py`).

Paired inference (matched seeds):
- **Perturbation/viewpoint factor** (MolmoBot, mobile@static vs +perturbed, same pipeline):
  Δ = **+13.8 pts** [6.0, 21.4]; McNemar **χ²(1)=14.8, p=4.9e-5 *** (paired n=144; 24 scenes
  flip success→fail under perturbation, only 3 the other way).
- **Radius magnitude** (logistic fit, success ~ r over realized r∈[0.02,0.66] m): slope flat,
  OR per +0.10 m ≈ 0.96, **n.s.** (p≈0.8). Degradation comes from the *presence* of a shift,
  not its size.

## Findings
1. **Floating base + contact alone barely dent MolmoBot** — 92.4% at the correct (static) pose
   under full physics. (The fixed-base static cell, 66.6%, is a *different in-process pipeline*,
   so do NOT read 66.6→92.4 as "mobility helps"; see caveat 1.)
2. **A perturbed start pose significantly degrades MolmoBot** (92.4%→78.6%, p<1e-4). The drop is
   driven by the *existence* of the viewpoint/approach shift, **not its magnitude** (flat radius curve).
3. **Scripted IK solves 100% at every radius** → all MolmoBot failures are policy failures under
   distribution shift, not geometric infeasibility.
4. **The gap is strongly architecture-dependent (RQ2):** genuine π0.5 (`pi05_droid`, Physical
   Intelligence) scores 0/15 at the same static baseline where MolmoBot reaches 66.6%. The earlier
   MolmoBot-Pi0 (a different model) was 1/43 = 2.3% — so BOTH π-family policies are at the floor while
   MolmoBot-DROID is not. They make structured pick/grasp/place attempts (not flailing) but don't satisfy
   the lift-hold criterion → see caveat 2. Because π0.5 is at the floor even in the easiest (static)
   condition, it has no measurable perturbation/radius degradation — there is nothing to plot as a
   π0.5 curve on Chart 2; it appears only as the r=0 point.

## Caveats (read before the poster)
1. **Floating-base factor is not cleanly isolated.** The static cell runs MolmoBot in-process on the
   fixed DROID franka (a different code path), while mobile@static runs the served-VLA hybrid. So the
   *clean* contrast is within the hybrid: mobile@static vs mobile+perturbed (the perturbation factor).
   The base-mobility-vs-fixed-base comparison mixes pipelines.
2. **π0.5 is heavily confounded — treat as a lower bound, not a clean capability measure.** The bar is
   the genuine `pi05_droid` (Physical Intelligence π0.5, 32-dim actions), loaded via openpi, run
   zero-shot. It is a pick-and-PLACE-trained policy that emits `place` subtasks and tends to release
   after lifting, run at 66 ms control dt vs MolmoBot's 200 ms. Success is the same PickTask (lift ~5 cm,
   1 cm threshold), so the 0% is real, but it reflects a policy/task + control-rate mismatch as much as
   capability. n=15 (thin; stopped early to free shared GPUs and /tmp). π0.5 in the mobile/perturbed
   conditions was NOT run: it would require wiring π0.5 into the mobile hybrid's grasp stage, and since
   π0.5 is already at the floor when static, a perturbed curve would be uninformative.
3. **Radius is a realized single offset**, dx,dy ~ U(−0.5,0.5)·scale, max 0.66 m. There is **no**
   controlled r∈{0.1,0.25,0.5,1.0} sweep and r=1.0 m is unreachable (max 0.707).
4. **n varies per cell** (runs stopped at solid n to free the shared school GPUs; all sweeps are
   resumable from their jsonl): static n=347 (complete), mobile@static n=144 (converged ~92%),
   mobile+perturbed n=204, pi0.5 n=43. Success rates were stable across rounds (cond3 held ~78%
   from n≈90 onward; pi0.5 ≤6% throughout), so the conclusions do not depend on the remaining scenes.
5. **Scripted = ceiling by construction** (the 347 set is defined as the scenes scripted IK solves
   under perturbation), so its 100% is a feasibility floor, not an independent result.
6. **Reproducibility verified:** all 1059 logged perturbations reproduce exactly from
   `seed = hash((0, house_index, episode_idx)) & 0xFFFFFFFF` → `RandomState.uniform(±0.5)·scale`.
7. **v2 supersession:** the first v2 charts double-perturbed (started from an already-perturbed pose +
   a second live offset, nav targeting the wrong origin). v3 fixes this via `MLSPACES_PERTURB_SCALE`
   on a true-original-pose benchmark.
